# Accept all standards-defined ML-KEM private key encodings in KAS

## Summary

KAS currently accepts only the 64-byte seed form of a pure ML-KEM private key.
Accept the three private-key alternatives defined by
[RFC 9935, Section 6](https://www.rfc-editor.org/rfc/rfc9935.html#section-6):
seed, expandedKey, and both. Keep emitting the existing seed form, which the
RFC recommends. In Go FIPS mode, load only the seed form because the other
forms require CIRCL in this implementation.

## Problem / Motivation

RFC 9935 defines a private-key CHOICE for each ML-KEM parameter set. The
ML-KEM-768 form is:

```asn1
ML-KEM-768-PrivateKey ::= CHOICE {
  seed [0] OCTET STRING (SIZE (64)),
  expandedKey OCTET STRING (SIZE (2400)),
  both SEQUENCE {
    seed OCTET STRING (SIZE (64)),
    expandedKey OCTET STRING (SIZE (2400))
  }
}
```

The ML-KEM-1024 form uses 3168-byte expanded keys. RFC 9935 also defines
ML-KEM-512 with 1632-byte expanded keys, which this repository does not
support.

Today, `parseKEMPrivatePKCS8` in `lib/ocrypto/mlkem.go` expects only the
`[0]` seed and rejects other inner tags. OpenSSL's default ML-KEM private-key
output contains both the seed and expanded key. Expanded-only keys from other
standard tooling are also rejected. This prevents KAS from loading those keys.

The supported pure ML-KEM algorithms are ML-KEM-768 and ML-KEM-1024.

## Proposed Solution / Implementation Plan

1. Update `parseKEMPrivatePKCS8` to select the inner key form by ASN.1 tag.
   Decode the seed (`[0]`), expanded key (`OCTET STRING`), or both (`SEQUENCE`
   of two `OCTET STRING`s). Require complete DER consumption and enforce the
   sizes associated with the algorithm OID: 64-byte seed, 2400-byte expanded
   ML-KEM-768 key, or 3168-byte expanded ML-KEM-1024 key. Reject unexpected
   tags, extra fields, trailing bytes, invalid versions, and mismatched OIDs
   with errors that identify the invalid form or length.
2. For the both form, derive an expanded key from the seed and compare it with
   the supplied expanded key. Reject an inconsistent pair, then use the seed
   for decapsulation. This catches malformed material at key load rather than
   during rewrap. Reject the both form at load time in Go FIPS mode because
   deriving the expanded key for this check uses CIRCL.
3. Keep Go's `crypto/mlkem` path for seed-based decapsulation. For an
   expanded-only key, import its serialized decapsulation key with the
   existing `github.com/cloudflare/circl/kem/mlkem` dependency and use it for
   decapsulation. Validate the key on import, including the hash check required
   by RFC 9935 Section 8 and FIPS 203 Section 7.3. Go's `crypto/mlkem` API
   cannot import an expanded key or recover its seed. Update the `mlkemKEM`
   and `newKEMDecryptor` validation path so both valid lengths load, while
   invalid keys still fail immediately. Reject expanded-only keys at load time
   in Go FIPS mode. Guard every CIRCL expansion, import, and decapsulation
   path so they cannot run while FIPS mode is enabled.
4. Leave `marshalKEMPrivatePKCS8` on the seed form. Keep the public-key SPKI,
   wrapped-DEK envelope, KAS rewrap protocol, and client behavior unchanged.
   The parsing code is in shared `lib/ocrypto`, so any consumer of
   `FromPrivatePEM` can accept the additional forms after upgrading, but no
   SDK client code change is needed.

## Inputs / Outputs / Contracts

- Input: unencrypted PKCS#8 `PRIVATE KEY` PEM with a registered pure ML-KEM
  algorithm OID and one of the three inner private-key encodings. In Go FIPS
  mode, only the seed encoding is accepted.
- Output: the existing KEM decryptor. KAS loads it through
  `service/internal/security/standard_crypto.go` or the basic key manager
  and uses it to unwrap the DEK during rewrap.
- Serialization output: the existing seed-only PKCS#8 encoding. No TDF,
  public-key, KAS API, or SDK wire-format change.

## Edge Cases & Constraints

- Validate the expanded key according to its parameter set, including the
  required hash check, before accepting it. An expanded key is not reversible
  to a seed.
- In Go FIPS mode (`GODEBUG=fips140=on` or `fips140=only`), reject expanded-only
  and both encodings before any CIRCL operation. Seed-only keys continue to
  use Go's `crypto/mlkem`. X-Wing also uses CIRCL; reject its key generation,
  private-key loading, encapsulation, and decapsulation in FIPS mode.
- Reject a both form when either component has the wrong length or the two
  components disagree. Do not silently ignore an inconsistent expanded key.
- Reject an ML-KEM-768 expanded key under the ML-KEM-1024 OID and vice versa.
- Keep the distinct X-Wing and P-256/P-384 hybrid PKCS#8 formats on their
  existing parser path. They use different inner private-key layouts; this
  ML-KEM CHOICE change does not extend their formats.
- Keep private test material explicitly test-only and out of production
  configuration.

## Testing Plan

1. Add table-driven `lib/ocrypto` tests for ML-KEM-768 and ML-KEM-1024 in
   seed, expanded-only, and both forms. For each, load through
   `FromPrivatePEM`, wrap with its public key, and verify decapsulation and
   DEK recovery. Confirm that newly serialized keys still use `[0]` seed.
2. Add malformed-input cases for wrong tags, lengths, OIDs, truncated DER,
   trailing bytes, extra sequence fields, failed expanded-key hash checks, and
   inconsistent seed/expanded-key pairs. Assert clear errors at load time.
3. Add an OpenSSL-generated default-format vector for each supported size,
   and a KAS test that loads those keys and completes rewrap. Record the
   OpenSSL version and fixture generation commands; keep test-only material
   isolated from production keys.
4. Run `make fmt`, `make lint`, `make test`, and
   `cd sdk && go test -run TestREADMECodeBlocks` before committing. If
   cross-SDK behavior needs validation, run xtest on the branch and confirm
   that the relevant tests ran rather than being skipped.
5. Run focused tests in both Go FIPS modes and confirm seed-only keys load
   while expanded-only and both keys fail at load time. Confirm all X-Wing
   operations fail before calling CIRCL.

## Out of Scope

- Changing how platform-generated ML-KEM private keys are written.
- Changing client SDKs or the public-key SPKI and wrapped-DEK formats.
- Adding ML-KEM-512 or changing hybrid/X-Wing private-key encodings.
- Switching the web SDK roundtrip workflow to OpenSSL. Its runner currently
  ships an OpenSSL version too old for ML-KEM; platform keygen remains the
  available path. The web SDK's ML-KEM ASN.1 decoder reads public SPKI only.

## Acceptance Criteria

- [ ] KAS loads default `openssl genpkey` ML-KEM-768 and ML-KEM-1024 private
      keys in the both form and completes rewrap with each.
- [ ] Seed-only, expanded-only, and both forms load and correctly decapsulate
      for ML-KEM-768 and ML-KEM-1024.
- [ ] Malformed, inconsistent, and size-mismatched keys fail with clear errors
      at load time.
- [ ] Regression vectors cover every accepted form and include OpenSSL
      default-format keys.
- [ ] Existing seed-form output and client interoperability remain unchanged.
- [ ] Go FIPS mode rejects expanded-only and both keys without running CIRCL;
      seed-only keys still load.
- [ ] Go FIPS mode rejects all X-Wing operations before calling CIRCL.
