# Accept all standards-defined ML-KEM private key encodings (seed / expandedKey / both) in KAS

## Summary
ProblemFor the pure ML-KEM KAS scenario, opentdf/platform's private-key parser accepts only one of the three standards-defined ML-KEM private-key encodings. This blocks interop with standard tooling.
draft-ietf-lamps-kyber-certificates defines the ML-KEM private key as a CHOICE:
ML-KEM-PrivateKey ::= CHOICE {
  seed        [0] IMPLICIT OCTET STRING (SIZE (64)),
  expandedKey     OCTET STRING (SIZE (1632|2400|3168)),
  both        SEQUENCE { seed OCTET STRING, expandedKey OCTET STRING }
}All three are valid. Today, lib/ocrypto/mlkem.go (parseKEMPrivatePKCS8) unmarshals the inner key strictly as tag:0,implicit OCTET STRING and errors on any trailing bytes, so it accepts only the seed [0] form. Consequences:
OpenSSL genpkey with default settings is rejected. OpenSSL 3.5's default output is seed-priv = the both SEQUENCE (seed + expandedKey), not seed [0].
FIPS expandedKey / priv-only (bare dk) keys are rejected. This is the form relevant to FIPS-certified software/hardware — directly relevant to this epic's CNSA 2.0 / FedRAMP High goals.
Evidence / contextPlatform writer & reader: lib/ocrypto/mlkem.go — marshalKEMPrivatePKCS8 / parseKEMPrivatePKCS8; keys are 64-byte seeds (d‖z) via Go stdlib crypto/mlkem.
The web-sdk roundtrip CI (opentdf/web-sdk PR #933, .github/workflows/roundtrip/init-temp-keys.sh) cannot use the runner's OpenSSL to make ML-KEM KAS keys — runner ships OpenSSL 3.0.13 (ML-KEM needs 3.5+), and even on 3.5 the default output form is incompatible — so it must shell out to the platform's own service/cmd/keygen. Broadening acceptance removes that constraint and lets any standard tool produce KAS keys.
OpenSSL default format: https://docs.openssl.org/3.5/man7/EVP_PKEY-ML-KEM/ and https://openssl-library.org/post/2025-01-21-blog-positionandplans/
Proposed changeIn opentdf/platform lib/ocrypto, make ML-KEM (and by extension the hybrid P256+ML-KEM / P384+ML-KEM / X-Wing) private-key parsing liberal in what it accepts — decode all three CHOICE alternatives:
seed [0] IMPLICIT OCTET STRING (64 bytes) — current behavior.
expandedKey OCTET STRING (1632 / 2400 / 3168) — reconstruct the decapsulation key directly.
both SEQUENCE { seed, expandedKey } — prefer seed; ignore or cross-check expandedKey (OpenSSL default).
Continue emitting the seed form on the write side (keep output stable). This is a read/parse-side tolerance change (Postel's law), not a wire-format switch.
Acceptance criteriaKAS loads a pure ML-KEM-768 and ML-KEM-1024 private key generated by openssl genpkey -algorithm ML-KEM-768/1024 with default settings (the both form) and completes a rewrap.
KAS loads keys in seed-only, priv-only (expandedKey), and both forms; round-trip decapsulation succeeds for all.
Malformed / size-mismatched keys still fail with a clear error.
Regression test vectors added for each accepted form (ideally including an OpenSSL-3.5-generated fixture).
Notes / follow-upsThe web-sdk ASN.1 decoder (lib/tdf3/src/crypto/core/mlkem-asn1.ts) only handles public SPKI (single form), so it is unaffected by the private-key CHOICE — but worth a glance for parallel tolerance if it ever reads private keys.
Once the platform accepts the standard forms, the roundtrip init-temp-keys.sh could optionally switch to OpenSSL when a new-enough version is available, though the platform keygen remains the simplest zero-dependency path.
