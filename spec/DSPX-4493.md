# Switch go-sdk i.v. nonce generation away from random to deterministic/sequential

## Summary
Use deterministic (e.g. sequential, depending on the writer mode) i.v. generation for BaseTDF / ZTDF writes

## Problem / Motivation

Every payload segment the Go SDK writes is encrypted with
`ocrypto.AesGcm.EncryptInPlace`, which is built on Go's
`cipher.NewGCMWithRandomNonce`. The 12-byte IV is drawn at random inside the
standard library and the writer never sees it. That is NIST SP 800-38D
**§8.2.2 (RBG-based)** IV construction, and §8.3 caps it at 2^32 invocations
per key precisely because uniqueness is only probabilistic. Over `n` random
96-bit IVs the collision probability is about `n²/2^97`.

The parent epic (DSPX-4502, *Large File TDF Security and Support*) targets
50 TiB payloads. At that scale the probabilistic bound stops being comfortable:

| payload | segment size | segments | P(IV collision) |
|---|---|---|---|
| 50 TiB | 16 KiB (`minSegmentSize`) | 2^31.6 | **2^-33.7** |
| 50 TiB | 2 MiB (default) | 2^24.6 | 2^-47.7 |
| 4 PiB | 2 MiB | 2^31 | 2^-35.0 |

A 50 TiB file written at the minimum segment size lands essentially *on* NIST's
approved §8.3 ceiling with no margin. A stream whose length cannot be measured
has no segment ceiling at all today — `maxPayloadSegments` bounds only the
declared-size path — so its exposure is unbounded. DSPX-4905 tracks that gap
separately.

An IV collision under a reused key is not graceful degradation. The two
ciphertexts XOR to the XOR of their plaintexts, **and** the GHASH subkey
becomes recoverable, which forges authentication tags for everything else
encrypted under that key.

Peer work: web-sdk DSPX-4496 (merged, `lib/tdf3/src/ciphers/gcm-iv-counter.ts`)
and java-sdk DSPX-4495. All three SDKs must land on the same layout.

## Proposed Solution

Switch the writer to SP 800-38D **§8.2.1 (deterministic)** IV construction:

```
byte  0 .. 7              8  9 10 11
     +--------------------+------------+
     | MessageID (64b)    | part (32b) |   big-endian
     | RBG, per TDF       | 0,1,2,...  |
     +--------------------+------------+
```

The fixed field (`MessageID`) is drawn once per TDF from a cryptographic RBG
and copied into every IV. The invocation field is the part number. Within one
message, non-repetition becomes a property of the construction rather than a
probability; across messages it still rests entirely on the fixed field being
drawn fresh, which is why a `MessageID` is never reused or derived.

**Part 0 is reserved for key access object metadata**; payload segment `i`
takes part `i + 1`. This is load-bearing, not cosmetic: `splitDEK` randomizes
all but the last share, so a single-split TDF's only share *is* the DEK
verbatim, and its metadata is sealed under the payload key. Without the
reservation, the metadata and segment 0 would share an IV.

**The part number is derived from the segment index, not from a counter.**
`chunkedWriter.WriteSegment(ctx, index, data)` accepts sparse, out-of-order and
concurrent indices, so `part = index + 1` is a pure function. A stateful
`next()` would need a mutex on the hot path, would burn a part number on every
retry, and would break the index↔part correspondence entirely.

**The wire format does not change.** The IV is still the 12-byte prefix of each
encrypted segment, and of each `EncryptedMetadata` blob. Readers take it off
the wire exactly as they already do, so this is writer-side only: no manifest
change, no spec version change, and no reader-side validation of the
construction (pre-existing TDFs with random IVs must keep decrypting forever).

**The new `ocrypto` API is not written around IVs.** libsodium
(`crypto_secretstream`), Google Tink (`StreamingAEAD`), Rust `aead::stream` and
the AWS Encryption SDK all converge on the same shape: a keyed object built
from a per-message random value and addressed by an ordinal, with no raw nonce
bytes in the public API. We follow that, diverging only in making the ordinal
an explicit argument rather than an auto-advancing counter.

Fusing the key and the message ID at construction is the point. The rejected
alternative — a nonce factory plus an explicit-IV cipher — leaves the writer
holding two independent values that a later refactor can desynchronize, and
pairing one message's ID with another message's key is silent cross-file IV
reuse: the exact failure this work removes.

## Inputs / Outputs / Contracts

New in `lib/ocrypto/message_sealer.go`:

```go
const MessageIDSize = GcmStandardNonceSize - 4 // 8

var ErrInvalidMessageID            error
var ErrMessagePartsExhausted       error
var ErrMessageInvocationsExhausted error

// MaxMessageParts is the exclusive upper bound on the part numbers one key
// may seal: 2^32-1 with the deterministic construction, 2^26 on the RBG
// fallback, where it doubles as the key's encryption budget.
func MaxMessageParts() uint32

type MessageID struct{ /* opaque */ }

func NewMessageID(r io.Reader) (MessageID, error)
func MessageIDFromBytes(b []byte) (MessageID, error)
func (m MessageID) Bytes() []byte

type AesGcmSealer struct{ /* opaque */ }

func NewAESGcmSealer(key []byte, id MessageID) (AesGcmSealer, error)

// Seal returns the part's 12-byte header (the IV) and its ciphertext-with-tag,
// separately: callers hash them separately.
func (s AesGcmSealer) Seal(part uint32, plaintext []byte) (header, ciphertext []byte, err error)
```

There is deliberately no `Unseal`. `lib/ocrypto/aes_gcm.go` is untouched;
`Encrypt`/`Decrypt` remain correct for one-shot key wrapping.

Changed in `sdk/`:

```go
const metadataPart uint32 = 0            // reserved
var maxPayloadSegments int64             // min(ocrypto.MaxMessageParts()-1, MaxInt32)
var defaultSegmentSize int64             // derived; see below
func segmentPart(index int) (uint32, error)

var ErrChunkedMetadataChanged        error
var ErrChunkedSegmentIndexExhausted  error

type segmentSealer interface {
	Seal(part uint32, data []byte) (header, ciphertext []byte, err error)
}
type segmentSealerFactory func(dek []byte, id ocrypto.MessageID) (segmentSealer, error)

// metadataSealer is a capability, not a value: a closure already bound to
// metadataPart, so a key access resolver cannot ask for part 7 and collide
// with payload segment 6.
type metadataSealer func(key []byte, plaintext string) (string, error)

// keyAccessResolver gains the sealer.
resolve(ctx context.Context, dek []byte, seal metadataSealer, cfg *chunkedFinalizeConfig) (string, []KeyAccess, error)
```

A per-TDF `messageSealers` registry holds one sealer per distinct key, all
sharing the message's single ID, keyed by a copy of the key bytes (never by
split ID or KAS URL, which can change while the key does not). Where the
payload key and a share key coincide, both reach the same sealer, which is what
keeps the metadata and segment 0 numbered against one another.

No public SDK signature changes. `EncryptedMetadata`'s wire shape is unchanged,
and its `Iv == Cipher[:12]` relationship now holds by construction rather than
by the coincidence of a random nonce prefix.

## Edge Cases & Constraints

### FIPS 140-3

`cipher.NewGCM` — the only standard-library route to a caller-supplied IV — is
refused outright under `GODEBUG=fips140=only`: *"use of GCM with arbitrary IVs
is not allowed in FIPS 140-only mode"*. Under `fips140=on` it still succeeds,
but `GCM.Seal` records the operation as a **non-approved service**
(`fips140.RecordNonApproved`) where `SealWithRandomNonce` records an approved
one.

`ocrypto` therefore degrades internally: policy first (`fips140.Enabled()` →
random IVs), then a construction probe as a secondary check for
`fips140=only` and for any future restriction. The fallback is total — same
API, same wire bytes, same call sites — and the `MessageID` is drawn but
unused. **Nothing outside `lib/ocrypto` branches on FIPS mode.**

A probe-only design was rejected: it would silently keep deterministic IVs
under `fips140=on`, which is a production FIPS deployment, and record every
segment encryption as non-approved.

`fips140.Enforced()` and `fips140.WithoutEnforcement()` are Go 1.26; these
modules declare `go 1.25.0`, and silently disabling an enforcement an operator
asked for is the wrong trade regardless.

Two notes for the other SDKs:

1. **This is a Go restriction, not a NIST one.** SP 800-38D §8.2.1 explicitly
   approves the deterministic construction, and Go's own FIPS module
   implements one (`NewGCMWithCounterNonce`, FIPS 140-3 IG C.H Scenario 3) —
   but it is unexported and uses a 32-bit prefix with a 64-bit
   strictly-increasing counter, incompatible with both our 8‖4 split and with
   out-of-order indices.
2. **The fallback and its 2^26 cap are Go-specific** and should *not* be
   mirrored by DSPX-4495 or DSPX-4496.

### Exhaustion

`MaxMessageParts()` is the single enforcement point, range-checked by `Seal` in
both modes. It never wraps: reusing a part number under one key is the failure
this work exists to prevent, so exhaustion is a hard error.

On the RBG fallback the cap drops to 2^26 and also bounds encryption
*attempts*, since every call draws a fresh IV — a retry costs budget even
though it does not cost an ordinal. 2^26 is chosen from the birthday bound:

| max parts | `P(collision)` | @16 KiB | @2 MiB | @4 MiB |
|---|---|---|---|---|
| 2^32 (NIST §8.3 ceiling) | 2^-33 | 64 TiB | 8 PiB | 16 PiB |
| **2^26 (chosen)** | **2^-45** | 1 TiB | 128 TiB | **256 TiB** |
| 2^24 | 2^-49 | 256 GiB | 32 TiB | 64 TiB |

2^26 sits 6 bits under NIST's approved ceiling — a 4096× margin on collision
probability — while still clearing the epic's 50 TiB target by 5× at the
maximum segment size. 2^24 would not.

The SDK derives its sizing from that one number rather than learning about
FIPS: pick the smallest segment size at or above 2 MiB, capped at the 4 MiB
`maxSegmentSize`, such that `maxPayloadSegments × size ≥ 256 TiB`.
Deterministically that leaves 2 MiB unchanged; on the fallback it yields 4 MiB.
**The recommended segment size and the maximum segment count are the entire
application-visible surface of FIPS mode.**

### Retry

Retrying a failed index re-derives the same IV, so a retry carrying *different*
bytes would be a second encryption under one key and IV. That cannot happen as
`WriteSegment` is written today: every failure path from the seal to the
archive write is a bare error return that constructs no result, the archive is
handed a length and a CRC rather than bytes, `CleanupSegment` rolls even that
back or fences the writer, and an index the archive accepted can never be
retried. At most one ciphertext per (key, IV) ever leaves the function.

That is a property of the error handling, not of the IV construction, and is
one refactor away from being false. The invariant is recorded in a comment at
the encryption site.

### Repeated manifest builds

`GetManifest` and `Finalize` re-resolve key access on *every* call, each with
that call's own `WithChunkedEncryptedMetadata`. Combined with part 0 being
spent on the first value — and, for a single-split TDF, sealed under the DEK
itself — `GetManifest("A")` followed by `Finalize("B")` would be two plaintexts
under one key and IV. The first build pins the value; a later build offering a
different one fails with `ErrChunkedMetadataChanged`. Empty metadata pins too,
and the pin survives a failed build: what is spent is the part number, not the
manifest.

`SDK.CreateTDF` is immune by construction — `staticKeyAccess.resolve` returns
cached KAOs — and its metadata is sealed once, up front.

### Other

* `AesGcmSealer` is safe for concurrent use; copies share one encryption
  budget. Caching the AEAD is a small win over today's per-segment
  `NewGCMWithRandomNonce`.
* Registry keys are secret material and are never logged or put in an error
  message; a bad key is reported by length only.
* A registry entry is never dropped and rebuilt, which would reset that key's
  encryption budget on the fallback. Repeated splits mint fresh share keys and
  so add entries — a bounded but real memory cost on a writer that finalizes
  many times.

## Out of Scope

* **Readers.** Nothing validates the construction on the way back in; TDFs
  written with random IVs must keep decrypting indefinitely.
* **Manifest / spec version.** The wire format is unchanged, so neither moves.
* **java-sdk (DSPX-4495) and web-sdk (DSPX-4496).** Tracked separately; the
  FIPS fallback here is Go-specific.
* **The unmeasurable-stream segment ceiling.** A payload whose length cannot be
  established is still read to EOF with no ceiling. DSPX-4905.
* **`ocrypto.AesGcm`.** `Encrypt`/`Decrypt` keep random nonces; they are
  correct for one-shot key wrapping and have callers across `otdfctl`,
  `service` and `sdk`.
* **Risk quantification for the existing random construction.** DSPX-4492.

## Acceptance Criteria

- [x] Payload segment `i` is sealed at part `i + 1`, under a fixed field drawn
      once per TDF from a cryptographic RBG and copied into every IV.
- [x] Key access object metadata is sealed at part 0 of the same message, and
      no payload segment can take part 0.
- [x] Where the payload key and a split share key coincide, both reach the same
      sealer, so their part numbers are allocated against one another.
- [x] Sparse, out-of-order and concurrent `WriteSegment` calls each produce the
      IV their index implies, and all IVs in one message are distinct.
- [x] A retried segment index re-derives the same part number rather than
      consuming a new one.
- [x] A part number at or above `MaxMessageParts()` is a hard error; the
      construction never wraps.
- [x] A second manifest build with different encrypted metadata fails with
      `ErrChunkedMetadataChanged`; the same value rebuilds to identical bytes.
- [x] `maxPayloadSegments × defaultSegmentSize ≥ 256 TiB` for both values
      `MaxMessageParts()` can take.
- [x] Where a caller-supplied IV is unavailable or non-approved, `ocrypto`
      falls back to random IVs with no change to any call site outside
      `lib/ocrypto`, and the SDK test suite passes unmodified under
      `GODEBUG=fips140=on`, and under `GOFIPS140=certified` with no `GODEBUG`
      override.
- [x] Encrypt-direction known-answer tests pin the IV byte layout against
      fixtures rather than against the implementation.
- [x] A TDF written under one FIPS mode decrypts under the other, in both
      directions — the fallback changes how the header is chosen, never what it
      means.
- [x] A TDF written by this branch decrypts with an unmodified reader, and one
      written before it still decrypts here, confirmed cross-SDK by xtest
      (go↔js, go↔java).
