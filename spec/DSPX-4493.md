# Switch go-sdk i.v. nonce generation away from random to deterministic/sequential

## Summary

Seal every ZTDF payload segment with a NIST SP 800-38D §8.2.1 deterministic IV
built from a per-key counter, falling back to random IVs where FIPS 140-3
requires it. Writer-side only; the wire format does not change.

## Problem / Motivation

The Go SDK used to encrypt each segment with `cipher.NewGCMWithRandomNonce`,
which is SP 800-38D **§8.2.2 (RBG-based)**. Over `n` random 96-bit IVs the
collision probability is about `n²/2^97`, and §8 caps it at 2^-32 per key.

The parent epic (DSPX-4502) targets 50 TiB payloads:

| payload | segment size | segments | P(IV collision) |
|---|---|---|---|
| 50 TiB | 16 KiB (`minSegmentSize`) | 2^31.6 | **2^-33.7** |
| 50 TiB | 2 MiB (default) | 2^24.6 | 2^-47.7 |

At the minimum segment size that is essentially *on* NIST's ceiling. #4203
(DSPX-4492) added a hard stop, `ErrAESGCMExhausted` at 2^32-1 encryptions per
DEK, but with random IVs uniqueness is still only a probability.

A collision is not graceful degradation: the two ciphertexts XOR to the XOR of
their plaintexts, and the GHASH subkey becomes recoverable, which forges tags
for everything else under that key.

Peer work: web-sdk DSPX-4496 (merged, `lib/tdf3/src/ciphers/gcm-iv-counter.ts`)
and java-sdk DSPX-4495. Cross-SDK rules: virtru-corp/adr#368; Go supplement:
virtru-corp/adr#373.

## Proposed Solution

```
byte  0 .. 7              8  9 10 11
     +--------------------+---------------+
     | fixed field (64b)  | counter (32b) |   big-endian
     | RBG, per sealer    | 0,1,2,...     |
     +--------------------+---------------+
```

`ocrypto.AesGcmSealer` owns one key, a fixed field drawn from `crypto/rand`
when it is built, and an atomic counter. Every `Seal` takes the next counter
value, so callers never supply an IV or an ordinal and cannot repeat one.

- **One sealer per DEK.** The chunked writer builds it once and uses it for
  every payload segment. Sparse, out-of-order, concurrent and retried writes
  each take a fresh IV.
- **Metadata gets a throwaway sealer.** Each sealing of a key access object's
  encrypted metadata uses a new sealer with its own fixed field. A
  `ChunkedWriter` with a key splitter re-seals metadata on every
  `GetManifest`/`Finalize`, and that is safe because each seal takes a new IV.
  `CreateTDF` seals it once, up front.
- **No wire change.** The IV is still the 12-byte prefix of each segment and of
  each `EncryptedMetadata` blob. Readers do not validate the construction, so
  TDFs with random IVs keep decrypting.
- **No caller-supplied IVs in the API**, after libsodium `crypto_secretstream`, Tink
  `StreamingAEAD` and the AWS Encryption SDK. There is no `Unseal`.

## Inputs / Outputs / Contracts

`lib/ocrypto/message_sealer.go`:

```go
var ErrSealerExhausted error

// MaxSeals is 2^32-1 on both IV paths.
func MaxSeals() uint32

type AesGcmSealer struct{ /* opaque; safe for concurrent use; do not copy */ }

func NewAESGcmSealer(key []byte) (*AesGcmSealer, error)

// Seal returns the 12-byte header (the IV) and the ciphertext-with-tag
// separately, because callers hash them separately.
func (s *AesGcmSealer) Seal(plaintext []byte) (header, ciphertext []byte, err error)
```

`sdk/`:

```go
type segmentSealer interface {
	Seal(data []byte) (header, ciphertext []byte, err error)
}
type segmentSealerFactory func(dek []byte) (segmentSealer, error)

const maxPayloadSegments = math.MaxInt32 // archive addressing

var ErrAESGCMExhausted               error // WriteSegment's error wraps it and ocrypto.ErrSealerExhausted
var ErrChunkedSegmentIndexExhausted  error // index >= maxPayloadSegments
```

No public SDK signature changes; `ErrChunkedSegmentIndexExhausted` is a new
exported sentinel. `EncryptedMetadata`'s `Iv == Cipher[:12]`
relationship now holds by construction.

## Edge Cases & Constraints

### FIPS 140-3

Under `GODEBUG=fips140=only`, Go refuses `cipher.NewGCM`, the only stdlib
route to a caller-supplied IV. Under `fips140=on` it works, but the module
records the `Seal` as a non-approved service.

So `ocrypto` decides once per process: if `fips140.Enabled()` is true, or
`cipher.NewGCM` fails, it uses `cipher.NewGCMWithRandomNonce`, so the module
draws the IV. The fallback is total and internal: same API, same wire bytes,
same `MaxSeals()`. Nothing outside `lib/ocrypto` branches on FIPS mode.

`fips140.Enforced()` would tell the modes apart, but it is Go 1.26 and would
raise the floor of a published module.

This is a Go restriction, not a NIST one, and the fallback should not be
mirrored by DSPX-4495 or DSPX-4496.

### Exhaustion

The sealer's counter is the key's only encryption budget, on both paths:

- It counts **attempts**. A failed or retried seal is not given back.
- It never wraps. `Seal` refuses before encrypting once 2^32-1 values are
  spent, and the writer reports that as `ErrAESGCMExhausted`.
- On the random-IV path, 2^32-1 encryptions is `P ≈ 2^-33`, inside
  SP 800-38D's 2^-32. A 2^26 cap was rejected: it would need a FIPS-only
  default segment size and would shrink what FIPS builds could already write
  after #4203.

The archive addresses at most `MaxInt32` segments, below the sealer's cap, so
that is the limit `CreateTDF` meets first. A payload of known size is refused
up front with `errTooManySegments`; a stream of unknown length fails at segment
index `MaxInt32` with `ErrChunkedSegmentIndexExhausted`. `CreateTDF` seals each
index once, so only a `ChunkedWriter` caller retrying failed writes can reach
`ErrAESGCMExhausted`.

### Same key, two sealers

In a single-split TDF the only share is the DEK itself, so the metadata sealer
and the payload sealer share a key and both count from 0. They are kept apart
by their independent 64-bit fixed fields: about a 2^-64 chance per metadata
seal.

### Other

- The IV no longer identifies its segment; concurrent writers take counter
  values in arrival order.
- The AEAD is built once per key, not once per segment.

## Out of Scope

- **Readers.** Nothing validates the construction on the way back in.
- **Manifest / spec version.** The wire format is unchanged.
- **java-sdk (DSPX-4495) and web-sdk (DSPX-4496).**
- **`ocrypto.AesGcm`.** `Encrypt`/`Decrypt` keep random nonces for one-shot key
  wrapping.
- **Risk quantification and the `ErrAESGCMExhausted` stop.** DSPX-4492 (#4203).
- **The rest of the unmeasurable-stream work.** DSPX-4905.

## Acceptance Criteria

- [x] Payload segments are sealed under one fixed field drawn per sealer from a
      cryptographic RBG, with a big-endian counter starting at 0.
- [x] Sparse, out-of-order, concurrent and retried writes all take distinct
      IVs; a retry takes a fresh one.
- [x] Key access metadata is sealed by its own sealer, and may change between
      manifest builds.
- [x] The sealer never wraps; exhaustion surfaces as `ErrAESGCMExhausted` and
      counts failed attempts. With an injected low-limit sealer it stops
      `CreateTDF` for known- and unknown-length input; with the real sealer
      `CreateTDF` stops at the segment-index limit first.
- [x] `MaxSeals()` and the default segment size are the same in every FIPS mode.
- [x] Where a caller-supplied IV is unavailable or non-approved, `ocrypto` falls
      back to random IVs with no change outside `lib/ocrypto`, and the SDK suite
      passes under `GODEBUG=fips140=on`.
- [x] Encrypt-direction known-answer tests pin the IV byte layout against
      fixtures.
- [ ] A TDF written by this branch decrypts with unmodified readers, and older
      TDFs still decrypt here, confirmed cross-SDK by xtest (go↔js, go↔java)
      on the rebased branch.
