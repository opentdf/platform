# go-sdk: TDF reader panics and permissive validation on malformed archives (IsValidTdf / LoadTDF)

## Summary
Tracks GitHub issue opentdf/platform#4202 (reported against github.com/opentdf/platform/sdk v0.34.0).
sdk.IsValidTdf / sdk.LoadTDF are used by consumers (e.g. virtru-sdk-go Collaborate upload) to classify untrusted local files. Two malformed inputs panic the calling process, and one cleartext case passes validation. Confirmed still present on platform main @ 982df6d by source inspection.
1. ZIP64 length overflow → makeslice panicsdk/internal/zipstream/reader.go: a ZIP64 extra-field compressed size of 0xffffffffffffffff is narrowed with zipFileEntry.length = int64(bytesToRead) (reader.go:173) to -1. That passes the length > maxSize check in ReadAllFileData (reader.go:350), and readBytes then calls make([]byte, -1).
panic: runtime error: makeslice: len out of range
zipstream.readBytes(..., 0x2d, 0xffffffffffffffff) reader.go:375
zipstream.Reader.ReadAllFileData reader.go:354
zipstream.TDFReader.Manifest tdf3_reader.go:44
sdk.IsValidTdf sdk.go:489Repro: one 0.manifest.json central-directory entry with a 32-bit compressed size of 0xffffffff and a ZIP64 extra field carrying 0xffffffffffffffff.
This part duplicates DSPX-4687 (found earlier by static scan, not reproduced). This ticket now adds a runtime repro. Fix it under either ticket, then close the other.
Fix: in resolveEntryLocation, reject ZIP64 sizes/offsets above math.MaxInt64, and check them against the physical archive size. In ReadAllFileData / ReadFileData, reject negative lengths.
2. Statement.UnmarshalJSON nil dereferenceThis manifest passes lax schema validation, so IsValidTdf returns true, and then it panics in LoadTDF:
{"payload":{"type":"reference","url":"0.payload","protocol":"zip","isEncrypted":true},"encryptionInformation":{},
 "assertions":[{"id":"a","type":"other","scope":"tdo","appliesToState":"encrypted","statement":{"value":"ok"},"Statement":null}]}encoding/json matches field names case-insensitively, so the custom decoder also runs for "Statement": null. json.Unmarshal(data, &aux) sets aux to nil, and the next aux.Value dereferences it (sdk/assertion.go, Statement.UnmarshalJSON).
Fix: return early when the input is the JSON literal null, or guard aux after decoding. Consider also rejecting duplicate or case-variant keys in manifests generally.
3. Lax validation accepts payload.isEncrypted: falseIsValidTdf and LoadTDF with WithSchemaValidation(Lax) both accept a manifest that declares a cleartext payload. Callers that send IsValidTdf == true down a "verbatim, already-encrypted" path would reasonably expect it to be rejected. The flag is producer-asserted and unauthenticated. This is the same pattern as DSPX-4748 (Java reader trusts isEncrypted) and the DSPX-4703 / DSPX-4758 root-integrity hardening work. No SDK writer ever emits false, so validation should reject it, or at least IsValidTdf should.
Acceptance criteriaNeither malformed input panics. Both return a typed SDK error from IsValidTdf and from LoadTDF.
Add the fixtures as regression tests. The upstream fixtures are malformedZip64Manifest and staticPanickingManifestTDF in virtru-corp/virtru-sdk-go#347 (collaborate/files_upload_directory_test.go).
Add seed corpus entries for the existing zipstream / manifest fuzz targets so make fuzz covers both shapes.
Decide on and document the isEncrypted: false behaviour, preferably rejecting it.
Add an xtest container-mutation case (DSPX-4923) so the go, java and web readers are all held to "clean rejection, no crash" for these inputs.

## Problem / Motivation
`IsValidTdf` / `LoadTDF` classify untrusted files. A panic in either crashes the
calling process, and `IsValidTdf == true` for a manifest declaring a cleartext
payload lets callers treat unencrypted data as protected.

## Proposed Solution
1. **ZIP64 lengths.** Already bounded on main by DSPX-4590 (#4043): every
   ZIP64 size/offset is checked against the central directory start and the
   archive length before narrowing to int64, so the #4202 archive is rejected
   in `NewReader` (`file data at 45+18446744073709551615 runs past the start of
   the central directory`). This change adds the exact #4202 shape as a
   regression case (unit, `IsValidTdf`, `LoadTDF`, fuzz seeds) and
   defence-in-depth guards: `ReadAllFileData` and `readBytes` refuse negative
   lengths/indexes with `errZipFileSizeError` instead of reaching
   `make([]byte, n)`.
2. **`Statement.UnmarshalJSON`.** A JSON `null` (e.g. the case-variant
   `"Statement": null`) is now a no-op per the `json.Unmarshaler` convention,
   and the alias struct is decoded via `aux` rather than `&aux` so null can
   never reset it to nil. No other custom `UnmarshalJSON` exists in sdk/.
3. **`payload.isEncrypted`.** Cleartext-flagged TDFs are unsupported. Both
   `manifest.schema.json` and `manifest-lax.schema.json` now require
   `"const": true`, so `IsValidTdf` (lax) and `LoadTDF` with
   `WithSchemaValidation(Lax|Strict)` reject `false`. Writers already always
   emit `true` (all paths go through `chunkedWriter.buildManifest`); a test
   pins it.

4. **No default manifest size cap.** The 10 MB default (`defaultMaxManifestSize`
   in the SDK, `manifestMaxSize` in zipstream) is removed: DSPX-4502 targets
   50 TiB payloads whose manifests exceed 1 GiB (memory scaling is DSPX-4905).
   Forged ZIP sizes are stopped by the archive bounds checks, not a cap.
   `WithMaxManifestSize` remains an opt-in (must be > 0); internally a
   non-positive zipstream limit means unlimited.

## Inputs / Outputs / Contracts
- `IsValidTdf`: returns `false` + wrapped error for both malformed ZIP64 and
  `isEncrypted:false` (`ErrInvalidPerSchema`).
- `LoadTDF`: default schema validation is `Skip`, so default-config `LoadTDF`
  does **not** reject `isEncrypted:false`; the reader ignores the flag and
  always decrypts/verifies, so the flag cannot downgrade a read.

## Edge Cases & Constraints
- The null-statement manifest is schema-valid, so `IsValidTdf` still returns
  `true` for it (it no longer panics anywhere); `LoadTDF` decodes it and the
  first read fails integrity checks. Rejecting duplicate / case-variant keys
  generally is a possible follow-up (assertion statement values are
  arbitrary JSON objects, so a blanket rule needs care).
- `FuzzLoadTDF` previously failed every input at the KAS allowlist lookup and
  never reached the manifest parser; it now ignores the allowlist.

## Out of Scope
- xtest container-mutation case (DSPX-4923) for go/java/web readers.
- Hard reject of `isEncrypted:false` on the schema-skipping read path.

## Acceptance Criteria
- [x] Neither malformed input panics `IsValidTdf` or `LoadTDF`.
- [x] Fixtures added as regression tests and fuzz seeds.
- [x] `isEncrypted:false` rejected by both schemas and `IsValidTdf`.
- [ ] xtest mutation case (DSPX-4923).
